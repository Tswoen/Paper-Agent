# 会话存储设计方案（草案）

## 1. 背景

当前系统已经具备一次完整会话的执行能力，但缺少对“会话过程”的持久化能力。为了让用户能够回看历史会话、查看执行过程、追踪中间状态，并为后续的恢复、审计和分析做准备，需要设计一套稳定的存储方案。

这里的重点不是只保存最终结果，而是保存一次会话从创建、执行、更新到结束的全过程。

## 2. 设计目标

- 保存每一次会话的完整历史记录。
- 支持按用户查看历史会话列表。
- 支持进入某一次会话后查看过程详情。
- 支持后续扩展恢复执行、失败重试、审计追踪。
- 先做单机可落地方案，后续再平滑扩展到更高并发或分布式场景。

## 3. 核心思路

存储层不要把“聊天记录”当成唯一核心，而要把“会话执行过程”当成核心对象。

也就是说，一次会话可以包含：
- 用户输入
- 系统分配的会话信息
- Agent 执行过程
- 中间事件日志
- 工具调用记录
- 最终输出
- 异常和失败信息

前端展示时，再根据这些存储数据组装成用户可读的历史会话页面。

## 4. 推荐方案

### 4.1 第一阶段

建议优先使用 `SQLite + 文件系统` 的组合方案：

- `SQLite` 保存结构化元数据。
- 文件系统保存大文本、日志片段、附件、导出文件等内容。

这样做的优点是：
- 部署简单。
- 适合当前单机项目。
- 开发成本低。
- 后续可平滑迁移到 PostgreSQL、MySQL 或对象存储。

### 4.2 目录建议

```text
data/
  session_store.db
  sessions/
    {session_id}/
      events.jsonl
      artifacts/
      exports/
      snapshots/
```

其中：
- `session_store.db` 负责主索引和查询。
- `events.jsonl` 负责按时间顺序记录过程事件。
- `artifacts/` 负责存放会话产生的附件或中间产物。

## 5. 核心数据模型

### 5.1 会话主表 `session`

用于表示一次完整会话。

建议字段：
- `id`：会话唯一标识，建议使用 UUID。
- `user_id`：所属用户。
- `title`：会话标题，支持自动生成和手动修改。
- `status`：`created` / `running` / `paused` / `completed` / `failed` / `cancelled`
- `created_at`：创建时间。
- `updated_at`：更新时间。
- `last_message_at`：最后一次交互时间。
- `summary`：会话摘要，便于列表快速展示。
- `metadata`：扩展字段，JSON 格式。

### 5.2 过程事件表 `session_event`

用于记录会话过程中的每一步变化。

建议字段：
- `id`
- `session_id`
- `event_type`
- `content`
- `created_at`
- `seq_no`
- `metadata`

事件类型可以包括：
- `user_message`
- `assistant_message`
- `tool_call`
- `tool_result`
- `status_change`
- `error`
- `summary_update`

### 5.3 消息表 `session_message`

如果后续需要更强的聊天展示能力，可以单独拆出消息表。

建议字段：
- `id`
- `session_id`
- `role`：`user` / `assistant` / `system`
- `content`
- `created_at`
- `parent_id`
- `metadata`

### 5.4 产物表 `session_artifact`

用于保存会话产生的文件、图片、导出内容等。

建议字段：
- `id`
- `session_id`
- `artifact_type`
- `name`
- `path`
- `size`
- `created_at`
- `metadata`

## 6. 读写流程

### 6.1 创建会话

用户发起新任务时：

1. 创建 `session` 记录。
2. 写入初始用户输入。
3. 生成首个 `session_event`。
4. 返回会话 ID，供前端继续追加展示。

### 6.2 执行过程中

Agent 每产生一个关键动作，就写入一条事件：

- 开始执行
- 调用工具
- 工具返回
- 中间摘要更新
- 发生异常
- 状态切换

这样可以保证即使任务中断，也能复原执行轨迹。

### 6.3 结束会话

会话结束时：

1. 更新 `session.status`。
2. 写入最终摘要。
3. 更新 `updated_at`。
4. 如有导出文件，写入 `session_artifact`。

## 7. 查询能力

前端至少需要两类查询：

- 会话列表查询：按用户、时间、状态、标题模糊搜索。
- 会话详情查询：按 `session_id` 拉取主表、消息、事件、产物。

建议列表页只查主表和摘要，不一次性加载全部事件，避免数据过多影响响应速度。

## 8. 版本策略

建议给存储结构预留版本号。

原因是：
- 后续字段可能会变。
- 前端展示形式可能会变。
- 事件结构可能会继续细化。

可以在 `metadata` 中保留 `schema_version`，后续升级时做兼容处理。

## 9. 落地顺序

建议按下面顺序推进：

1. 先定义会话主表和事件表。
2. 再把当前执行过程接入事件写入。
3. 然后补历史会话列表和详情查询接口。
4. 最后再补摘要、导出、恢复执行等能力。

## 10. 待确认问题

后续我们可以继续一起补充这些点：

- 需不需要支持多用户隔离？
- 会话是否允许用户手动重命名？
- 事件粒度要细到什么程度？
- 是否要支持恢复某一次中断会话？
- 是否需要把附件和大文本拆到文件存储？

## 11. 暂定结论

这套方案的核心是：

- 用 `session` 作为会话主索引。
- 用 `session_event` 记录全过程。
- 用文件系统保存大体积产物。
- 先做单机可用版本，再逐步升级。

这是一版可落地的起步设计，后面可以根据你的业务流程继续细化表结构、接口和前端展示方式。
